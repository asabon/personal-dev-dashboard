# 単体テストの完全性維持ルール (`testing-integrity`)

本体コードの修正・機能追加を行う際、「テストを通過させるためだけに既存のテストコードを都合よく書き換える（テストの形骸化・同語反復化）」ことを防ぐため、すべての AI コーディングエージェントは実装時に以下のルールを厳守してください。

---

## 🛡️ 実装時の基本原則（事前防止）

1. **既存テストが失敗したときの第一原則（本体コードのデグレを疑う）**:
   - 本体コードを変更した後に既存のテストが失敗した場合、**「テストが古いから直す」のではなく、「今回の本体コードの変更が既存仕様を壊した（リグレッション）」とみなして本体コード側のロジックを見直してください**。
2. **「既存テストは無変更でパスさせ、新規テストを追記する」アプローチ**:
   - バグ修正や機能追加では、原則として **既存の `it(...)` ブロックや `expect(...)` アサーションには手を加えず、新しい振る舞いやエッジケースを検証する `it(...)` を追加** してください。
   - テストを通過させる目的で、既存の `expect(...)` を削除・緩和したり、エラーが出ないようにモックデータを都合よく書き換えたりすることは厳禁です。
3. **不変条件（Invariants）テストの絶対保護**:
   - [`src/services/security.test.ts`](../../src/services/security.test.ts)（通信先ホワイトリスト・PAT 非漏洩・CSP 検証）および [`src/services/storage.test.ts`](../../src/services/storage.test.ts)（過去の設定 JSON の後方互換性・マイグレーション）の既存アサーションは、いかなる機能変更であっても緩和・削除してはなりません（新しい API 関数や新設定項目のテストケース追加のみ許可します）。
4. **実装詳細ではなく「仕様（ユーザー視点の振る舞い）」をテストする**:
   - 内部変数名や細かい実装手順に依存した壊れやすいテストではなく、[`docs/dev/ui-design.md`](../../docs/dev/ui-design.md)・[`docs/dev/api-design.md`](../../docs/dev/api-design.md)・[`docs/dev/testing.md`](../../docs/dev/testing.md) に定義された「仕様（入力に対する出力・DOM 表示・エラー/空状態遷移）」を検証するテストを作成してください。

---

## 🔍 既存テストの変更が許容される唯一の例外と手順

既存のテストケース（期待値やモック）を変更・削除してよいのは、以下の条件を満たす場合のみです。

- **許容条件**:
  - ユーザーから明示的に依頼された **「仕様変更（UI 文言・表示条件・データ構造・API 仕様の変更）」そのもの** によって、旧仕様を前提としたテストの期待値が成立しなくなった場合。
- **変更時の義務**:
  1. 既存テストを書き換える前に、「本体コードのバグではなく、意図された仕様変更によるものか」を自己確認する。
  2. 変更範囲は仕様が変わった箇所（例: ラベル文字列の変更など）の最小限に留め、同じテストケース内の他の検証（エラー状態や件数検証など）を弱めない。
  3. ユーザーへの完了報告および PR 本文に **「どの仕様変更に伴い、どの既存テストの期待値を更新したか」** を明記する。
  4. Push 前の [`local-review`](../skills/local-review/SKILL.md) にて、既存テストの差分（`-` 行）が正当な仕様変更に基づくものであることをサブエージェントに検証させる。
