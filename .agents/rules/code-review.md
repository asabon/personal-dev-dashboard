# コードレビュールール (`code-review`)

実装中・コミット前・PR 作成前・レビュー修正時などにおいて、コードの品質を担保し CodeRabbit（無料プラン）のレート制限を節約するため、以下の観点と手順で **コードレビュー（`code-review` スキル）** を実施してください。

## 1. 実行タイミングと独立視点の活用

- **任意のタイミング（オンデマンド）**:
  - ユーザーから「コードレビューして」「差分をチェックして」と指示された場合、または実装が一通り完了したコミット前の段階で実行します。
- **PR 作成・Push 前の必須実行**:
  - 新規 PR 作成時やレビュー指摘修正の `git push` を行う前に、必ず一度レビューを実施し、指摘事項（Critical / Major / 妥当な Nitpick）をすべてローカルで修正・検証してから **1 回の Push にまとめて** 反映してください。
- **独立サブエージェント（`research`）の活用**:
  - 実装を行ったエージェント自身がそのままコードを眺めると「実装者バイアス（思い込み）」によりエッジケースを見落としやすくなります。複数ファイルにまたがる変更では、`research` サブエージェントを起動して客観的に差分（`git diff main`）を検査させてください。

## 2. 必須チェックリスト（重点レビュー観点）

### A. 状態遷移・初期ロード・エラー時の UI 整合性
- **`isLoading=true` 時の誤表示防止**:
  - 初回ロード中に、データがまだ空（`[]`）であることを理由に `All Passed` や `0 PR`、`0件（正常）` のような「正常完了バッジ」が表示されてしまわないか。
  - 逆に、バックグラウンド自動更新（`isSilent = true`）時に毎回 `isLoading: true` になって画面全体がスピナーに置き換わるちらつきが発生しないか。
- **部分失敗・警告（`warning` / `incompleteCoverage`）の扱い**:
  - 一部のリポジトリや Organization の取得に失敗・スキップされた際、取得できた分だけで「すべて正常（`All Passed`）」と誤認させる表示になっていないか。
  - カード内のエラー・警告表示と、上部 `DashboardSummaryBar` の `FeatureAlert`（デバッグシナリオ含む）が整合しているか。
- **空状態（Empty State）とエラー状態の優先順位**:
  - エラーが発生しているリポジトリやデータが「0件だから非表示」のフィルタで消えてしまわないか。
  - エラーバナーの直下に緑チェックマーク付きで「問題ありません」という空状態メッセージが重複表示されないか。

### B. 集約・キャッシュ・データ変換ロジックの境界値
- **集約キーの衝突防止**:
  - 文字列結合で Map / Set のキーを作る際、異なる属性値同士が衝突しないようプレフィックスや一意な ID（例: `workflowId ?? workflowName`, `pr:${branch}` vs `workflow-latest`）を使っているか。
- **進行中（Active / Running）状態の保護**:
  - 最新状態のみを残す集約処理において、古い `in_progress` の実行が後続の完了済み実行によって隠蔽されないか。
- **モジュールスコープキャッシュの副作用**:
  - `githubApi.ts` 等にキャッシュやモジュール変数を持たせる場合、PAT 変更・手動更新・ログアウト時に適切にクリアされるか、また単体テスト間でキャッシュが残留してテストが干渉しないか。

### C. GitHub API 仕様・レート制限・セキュリティ
- **GitHub API レスポンス仕様の正確な理解**:
  - `total_count`（過去の累積総数）と `per_page`（今回取得件数）の意味を取り違えていないか。
  - `conclusion` の全パターン（`failure`, `timed_out`, `action_required`, `startup_failure` 等）を考慮しているか。
  - 配列フィールド（`workflow_runs`, `runners`, `nodes` 等）が欠落・非配列だった場合にクラッシュせず適切にエラー/警告扱いになるか。
- **Zero-Backend & PAT セキュリティ**:
  - 新しい API 関数を追加した場合、`https://api.github.com/` 以外への通信がないこと、PAT が Authorization ヘッダーのみに格納されることを `src/services/security.test.ts` でも検証しているか。

### D. レスポンシブ UI・レイアウト
- **モバイル幅（`sm:` 未満）でのはみ出し防止**:
  - フレックスコンテナ内の要素に不要な `shrink-0` が付いて折り返し（`flex-wrap`）や省略（`truncate` / `min-w-0`）を阻害していないか。複数バッジが並んだ際に `flex-wrap` で安全に折り返されるか。

### E. テストのアサーション強度とドキュメント整合性
- **テストの網羅性**:
  - 新しい設定項目や Feature ID を追加した場合、`src/services/storage.test.ts` に既存保存データの後方互換（デフォルト値補完）テストがあるか。
  - UI テストでバッジのテキストだけでなく、表示されるべきカード本体・エラーメッセージ・再描画（`rerender`）時の状態変化までアサートしているか。
- **ドキュメントとの一致**:
  - `README.md`、`docs/dev/ui-design.md`、`docs/dev/api-design.md` 等の説明が、実装された表示条件・API 仕様と完全に一致しているか。
