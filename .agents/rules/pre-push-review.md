# Push 前セルフレビュールール (Pre-Push Code Review)

CodeRabbit（無料プラン）のレート制限を節約し、初回 Push でのレビュー通過率を最大化するため、`git push`（特に新規 PR 作成時およびレビュー修正 Push 前）を行う前に、必ず以下の手順と観点で **CodeRabbit 相当の事前レビュー** を実施してください。

## 1. 独立した視点でのレビュー実施（サブエージェントの活用推奨）

- 実装を行ったエージェント自身がそのままコードを眺めると「実装者バイアス（思い込み）」によりエッジケースを見落としやすくなります。
- 変更規模が複数ファイルにまたがる場合は、Push 前に **`research` サブエージェント（または専用レビューサブエージェント）** を起動し、`main` ブランチとの差分および変更ファイルを客観的に検査させてください。
- 指摘された事項（Critical / Major / 妥当な Nitpick）はすべてローカルで修正し、`npm run typecheck`・`npm test`・`npm run build` を通してから **1 回の Push にまとめて** 反映してください。

## 2. 必須チェックリスト（CodeRabbit 頻出指摘観点）

### A. 状態遷移・初期ロード・エラー時の UI 整合性
- **`isLoading=true` 時の誤表示防止**:
  - 初回ロード中やリフレッシュ開始時に、データがまだ空（`[]`）であることを理由に `All Passed` や `0 PR`、`0件（正常）` のような「正常完了バッジ」が表示されてしまわないか確認する。
- **部分失敗・警告（`warning` / `incompleteCoverage`）の扱い**:
  - 一部のリポジトリや Organization の取得に失敗・スキップされた際、取得できた分だけで「すべて正常（`All Passed`）」と誤認させる表示になっていないか。
  - カード内の警告表示と、上部 `DashboardSummaryBar` の `FeatureAlert` が整合しているか。
- **空状態（Empty State）とエラー状態の優先順位**:
  - エラーが発生しているリポジトリやデータが「0件だから非表示」のフィルタで消えてしまわないか。

### B. 集約・キャッシュ・データ変換ロジックの境界値
- **集約キーの衝突防止**:
  - 文字列結合で Map / Set のキーを作る際、異なる属性値同士が衝突しないようプレフィックスや一意な ID（例: `workflowId ?? workflowName`, `pr:${branch}` vs `workflow-latest`）を使っているか。
- **進行中（Active / Running）状態の保護**:
  - 最新状態のみを残す集約処理において、古い `in_progress` の実行が後続の完了済み実行によって隠蔽されないか。
- **モジュールスコープキャッシュの副作用**:
  - `githubApi.ts` 等にキャッシュやモジュール変数（`latestRateLimit` 等）を持たせる場合、PAT 変更時に別トークンのデータを返さないか、また単体テスト間でキャッシュや状態が残留してテストが壊れないか。

### C. GitHub API 仕様・レート制限・セキュリティ
- **GitHub API レスポンス仕様の正確な理解**:
  - `total_count`（過去の累積総数）と `per_page`（今回取得件数）の意味を取り違えていないか。
  - 配列フィールド（`workflow_runs`, `runners`, `nodes` 等）が欠落・非配列だった場合にクラッシュせず適切にエラー/警告扱いになるか。
- **Zero-Backend & PAT セキュリティ**:
  - 新しい API 関数を追加した場合、`https://api.github.com/` 以外への通信がないこと、PAT が Authorization ヘッダーのみに格納されることを `src/services/security.test.ts` でも検証しているか。

### D. レスポンシブ UI・レイアウト
- **モバイル幅（`sm:` 未満）でのはみ出し防止**:
  - フレックスコンテナ内の要素に不要な `shrink-0` が付いて折り返し（`flex-wrap`）や省略（`truncate` / `min-w-0`）を阻害していないか。

### E. テストのアサーション強度とドキュメント整合性
- **テストの網羅性**:
  - 新しい設定項目や Feature ID を追加した場合、`src/services/storage.test.ts` に既存保存データの後方互換（デフォルト値補完）テストがあるか。
  - UI テストでバッジのテキストだけでなく、表示されるべきカード本体・エラーメッセージ・再描画（`rerender`）時の状態変化までアサートしているか。
- **ドキュメントとの一致**:
  - `README.md`、`docs/dev/ui-design.md`、`docs/dev/api-design.md` 等の説明が、実装された表示条件・API 仕様と完全に一致しているか。
